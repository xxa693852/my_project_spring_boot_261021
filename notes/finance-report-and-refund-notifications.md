# 第一版收退款報表與退款處理通知

本機實作，未部署 AWS，未代為執行真實退款、SMTP 或 LINE 推播。

## 操作

- 活動卡片入口與編輯視窗為「活動資料修改／收退款」。不能修改的活動仍能讀取付款紀錄與登記已處理的退款。
- 管理員先於藍新處理全額退款，再在本站填寫內部說明、按「登記已全額退款」。本站不呼叫金流退款 API。
- 成功後排入 Email 與 LINE 通知。未綁定 LINE 標示 NOT_BOUND；兩管道各自寄送。內部退款說明不寄給玩家。
- 登記重複送出時不改時間、不再建立通知。寄送失敗不撤回退款紀錄。SENT 僅表示外部服務接受，非玩家已讀或退款入帳。
- 「重新整理退款與通知狀態」查看排程結果。UNKNOWN、SENDING 需要人工確認，不自動重試，避免重複寄送。歷史退款不補發。
- 後台「報表匯出」預設台北本月，提供起日、迄日與下載 Excel；使用獨立管理員 Session，前台會員 Token 不可代替。

## 三張工作表

1. 統計摘要：區間收款、區間內標記已退款、兩者差額、目前待退款、異常付款金額與筆數。
2. 活動統計：區間內活動或有區間交易、目前待處理款項的活動。含活動資料、目前已報名人數及各種金額。不是累計報名或出席人數。
3. 交易明細：區間交易、目前待退款清單、目前異常付款清單，分區列示。同一訂單可出現在不同用途清單，不可跨區重複加總。

收款依 paid_at，退款依 refunded_at（管理員在本站標記時間）。起訖日均含當天，後端使用起日00:00至迄日次日00:00的半開區間，避免小數秒漏算。每筆付款獨立加總，不與多筆通知連接。

異常款 REVIEW_REQUIRED 若有 paid_at，已計入對應區間的收款，另列清單供核對；不再次加總。尚未付款與失敗訂單不列收款。

待退款與異常款為全部當前狀態，不受日期區間限制。即使金流已處理而管理員未回本站登記，本站仍列待退款。不還原歷史日期當時的待退款餘額。

每張表均標示查詢區間、同一產生時間與狀態快照說明，檔名含區間和產生時間。REPEATABLE_READ 唯讀交易確保查詢使用同一資料庫快照。報表下載後不更新。

收款減已退款尚未扣除待退款、場租、主持人費用、金流手續費及其他成本，不是純利潤。後台標記已退款不能保證玩家銀行帳戶或信用卡帳單已反映退刷。

## 資料庫與程式閱讀

- 只新增 V20__create_refund_notifications.sql。新表及全部欄位含繁體中文 COMMENT，含索引／外鍵說明；學習對照 README 指向正式檔。保留 V1～V19。
- 未查詢實際資料庫 migration 套用狀態，因此不回改既有版本。V20 待啟動時依正常 Flyway 套用，不 repair、不關閉驗證。
- RefundNotificationService.enqueue：在退款登記同一交易內保存收件人與內容快照。排程領取 PENDING 時以條件更新確保只有一個工作者取得；唯一鍵限制每付款、每管道一筆。
- FinanceReportService.export：查詢快照、驗證日期、計算金額，使用一般迴圈呼叫 POI 產生三張表，回傳 bytes 與檔名。
- FinanceReportController：回傳 Excel 下載標頭與 no-store。日期區間錯誤拋 IllegalArgumentException，交給既有 GlobalExceptionHandler 回 HTTP 400；後台權限由既有攔截器處理。
- 參考舊專案 Excel 匯出的 XSSFWorkbook、工作表、列、儲存格與 byte[] 流程。未修改舊專案。

目前不含成本、分級／部分退款、自動退款 API 或銀行入帳時間追蹤。

## 驗證結果

37 項相關 Java 測試通過（含跨期、精確日界、空資料、異常款、通知失敗獨立處理、防重複與後台驗證）；44 項前端測試通過（含台北月份預設、日期倒置、下載失敗復原及防重複）。Excel 以 POI 重新開啟檢查三張表、數字／字串型別、產生時間一致與輸入不當作公式；未在 Microsoft Excel 原生介面驗收。報表頁已用本機 Chrome 預覽。未連線實際 MySQL 套用 V20，未驗收真實 SMTP／LINE，未部署 AWS。

## 2026-11-22 Excel 排版與本機整合驗證

修正「先用預設欄寬計算列高，之後才設定欄寬」的順序問題。頁首只保留標題、查詢區間、產生時間，統計立即顯示；長篇口徑說明移至表尾並合併文字欄，列高依實際欄寬估算。加入中文字型、標題層次、條紋、數字靠右、活動篩選、凍結表頭與列印設定。

LocalPaymentReportIntegrationTests 使用本機 localhost:3306/dnd_event_prod_test。測試啟動正常 Flyway 已套用 V17～V20 至此測試 schema；正式本機 schema 與 AWS 未操作。本輪沒有新增或修改 migration。

新增三場測試活動及獨立測試會員，經真正 RegistrationService 建立付款保留；使用固定假金鑰產生測試站表單、模擬帶簽章通知，檢查無效簽章拒絕及重送不重複收款。付款共1200元，400元登記退款，200元待退款；再模擬其中活動已結束，實際透過管理員 Session 呼叫匯出 API，確認統計、活動與通知佇列紀錄。測試交易全部回滾，AfterTransaction 核對會員與活動未殘留。沒有向藍新送出交易，沒有真實扣款、Email 或LINE。

本機真實金流問題是回呼目的地：NotifyURL、ReturnURL、ClientBackURL 都由 NEWEBPAY_TEST_CALLBACK_BASE_URL 組成。之前使用 AWS ngrok，通知自然送往 AWS，與本機訂單資料不一致。現有本機此變數留空，這次依使用者選擇保留阻擋，未改為正式站，也未另開網路通道。真實藍新測試仍需獨立 HTTPS 通道指向本機8081，再填入該變數並重啟。不要沿用 AWS 的 ngrok，亦不要將本機 .env 上傳至 AWS。

產生測試 Excel 位於 target/report-preview/local-verified.xlsx，可直接本機開啟查看；其來源測試資料已回滾，因此是測試時刻的靜態快照。
