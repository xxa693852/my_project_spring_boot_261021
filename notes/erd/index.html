依本機測試資料庫的結構中繼資料及專案 migration 製作，未讀取會員、付款或權杖的實際資料。共 16 張業務表、1 張 Flyway 系統表；欄位與外鍵以實際資料庫為準。

看 ER 圖查英文／中文欄位未設定外鍵的資料表
如何閱讀：PK = Primary Key（主鍵）；FK = Foreign Key（資料庫外鍵）；UQ = Unique（單欄唯一）。1 → 0..N 表示一筆父資料可對應零至多筆子資料；1 → 0..1 表示零或一筆。所有外鍵子欄位目前均不可為 NULL。
總覽省略部分交叉關聯以方便閱讀；完整 16 條外鍵均列於下方欄位對照與分區圖。停權與取消歷程有兩個不同角色指向會員，圖上合併路徑並標註「兩條外鍵」。

沒有外鍵線，仍可能有業務關聯

下列資料表以編號或快照支援通知、登入與留言限制，但未設定實體外鍵，所以未畫成實線。資料表未連線不代表沒使用，也不代表應直接新增外鍵。

  • auth_tokens｜登入權杖紀錄：owner_type 與 owner_id 共同識別權杖持有者；owner_id 未設資料庫外鍵，不能只看編號就認定為某張表的外鍵。
  • event_cancellation_notifications｜活動取消通知紀錄：event_id 邏輯對應 events.id；member_id 邏輯對應 members.id。這張表未設定實體外鍵，活動名稱與時間另存通知快照。
  • event_reminder_deliveries｜活動行前提醒發送紀錄：registration_id 邏輯對應 registrations.id，也是本表主鍵，因此每筆報名最多一筆提醒紀錄；未設定實體外鍵。
  • comment_moderation_notifications｜留言管理通知紀錄：member_id 邏輯對應 members.id；comment_id 邏輯對應 event_comments.id。未設定實體外鍵，通知保留活動名稱與留言建立時間快照。
  • comment_write_limits｜留言頻率限制：member_id 邏輯對應 members.id，也是本表主鍵；未設定實體外鍵。三個 BIGINT 時間欄位是程式 Clock.millis() 的毫秒時間戳，並非 DATETIME。
